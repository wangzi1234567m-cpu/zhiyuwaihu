# 状态机和业务安全

审核结论由业务系统提供。Agent解释已有结论，不自动做材料鉴真或入驻批准。关单方式由代码结合当前申请单和已审规则计算，不能由LLM任意选工具。

## 关单规则

来源：主表《场景汇总》A2，场景级渠道来自D13:D80。优先级是本设计对原文的显式解释，冲突走人工：

1. 商家主动要求驳回并回电告知原因、或有越级投诉／外部曝光风险：需要电话告知，优先于常规京麦和次数分支。普通咨询是否也覆盖须确认。
2. 无例外且相同场景第三次及以上错误提交：京麦驳回。
3. 主表渠道为京麦：不强制外呼。
4. 主表渠道为电话：先尝试告知。首次错误提交且未接通，可京麦驳回；第二次错误提交且未接通，创建跟进事件预约再次外呼，再次未接通后京麦驳回。

`submission_attempt`为同商家／同申请业务／同场景错误提交次数；`call_attempt`是本次提交的联系次数，不能混为一个retry_count。例外要求回电但持续不通的最终关单策略资料不明确，先人工处理，不套用普通未接通直接关单。拒绝、错人、静音超时不自动视为未接通。

## 状态与守卫

| 状态 | 输入／守卫 | 下一步 |
|---|---|---|
| CASE_READY | 服务器加载预授权申请单，规则可用 | ROUTING；规则冲突→MANUAL_REVIEW |
| ROUTING | 代码计算渠道，输出decision_id＋case_revision＋rule_version | 电话→OPENING；京麦→ACTION_READY |
| OPENING | 自报身份与模拟AI说明 | VERIFYING |
| VERIFYING | 对方最终输入确认匹配公司／店铺；否定或非联系人 | 匹配→EXPLAINING；错人→CLOSING，禁止口头披露和自动驳回 |
| EXPLAINING | 工具事实＋必填槽位＋已审模板 | QA；缺依据→MANUAL_REVIEW |
| QA | 操作、标准、质疑、来源、通过预期等意图 | 回答有依据则继续；改问另一申请单须重新授权，不切换主体 |
| QA | 商家表达理解／拒绝／预约请求 | 记录真实结果；预约→CALLBACK_PENDING；其他→CLOSING |
| CALLBACK_PENDING | 明确日期时间／时区／范围，经最终输入确认 | 幂等创建预约，不因模型提议就建预约 |
| CLOSING | 礼貌结束；记录告知完成／未完成 | ACTION_READY或MANUAL_REVIEW |
| ACTION_READY | 既定审核结论有效、case revision一致、当前渠道决策成立 | EXECUTING |
| EXECUTING | 工具确定成功／失败／超时 | WRITEBACK_PENDING／人工／RECONCILING |
| RECONCILING | 原operation查询 | 查明后回写；持续未知人工，禁止换key重提 |
| WRITEBACK_PENDING | 回写成功 | CLOSED；失败只重试回写，不重复驳回 |

电话路径需有已核对接听方和已告知证据，或资料允许的未接通例外，才能执行模拟京麦驳回。理解确认不是后台驳回授权；驳回依据是预授权审核任务和代码决策。商家拒听时停止，默认转人工确认后续处理，避免用未完成告知冒充完成。京麦-only分支无需假装有语音核验，但只能处理服务器预授权任务。

取消与并发：短事务锁申请单／CAS revision→检查权限和决策→持久化operation→派发→独立事务记结果。重复请求同key同payload返回原结果，不同payload冲突。唯一键覆盖application_id＋case_revision＋action_kind，防跨session重复驳回；预约再绑定确认记录与预约窗口。查证未知不得判失败。商家改变预约时间使旧预约确认失效，已创建预约需显式改期操作，不创建第二个未关联预约。

不能说补齐必过，不能推测品牌方真实联系人全号，不能让商家在通话中读出证件全文或上传真实资料到演示系统。工号使用模拟值且明示演示，是否保留工号是待确认话术规则。
